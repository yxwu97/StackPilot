# P2A-06 Evidence - Python venv Runner

Status date: 2026-08-18

P2A-06 and Phase 2A are verified. Windows manifests can bind a process service to a workspace-local Python virtual environment, and the server advertises `phase2.python-venv`.

## Delivered behavior

- `virtualEnvironment` is required for `runner: python-venv` and forbidden for every other runner by both JSON Schema and semantic validation.
- Registration joins and canonicalizes the relative venv path, rejects missing directories, and rejects symlink or junction escapes from the real workspace root.
- Start preflight repeats the trust-boundary check and resolves only `<virtualEnvironment>/Scripts/python.exe`; it never falls back to PATH, a global Python, an activation script, or a caller-provided command.
- The resolved executable is hashed, probed with the fixed `--version` argument under the existing bounded timeout/output rules, parsed as `Python <version>`, and recorded with resolution kind `venv`.
- Both daemon and oneshot Process Driver paths receive the same immutable resolved command and existing Job Object, identity, logging, readiness, cancellation, and stop controls.

## Automated verification

Schema and manifest tests cover valid binding, missing binding, non-Python misuse, missing paths, and link escape. Windows Runner tests cover exact interpreter selection, digest/version output, missing and outside paths, whole-venv junction escape, `Scripts` junction escape, and unsafe direct requests. Orchestrator tests verify the shared preflight path, and the existing Process Driver suite remains the lifecycle authority.

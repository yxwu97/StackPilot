# P0-04 Verification Evidence

## Scope

P0-04 establishes the `chi` HTTP router, `/api/v1` boundary, unified JSON error envelope, request trace IDs, health/version endpoints, OpenAPI baseline, and stable error-code registry.

Status: `verification`

The implementation and automated checks are complete in the current uncommitted worktree. Remote GitHub verification remains unavailable because Git cannot acquire credentials.

## Contract decisions

- Availability routes are `GET /health/live`, `GET /health/ready`, and `GET /version`.
- Stateful JSON responses use `application/json; charset=utf-8` and `Cache-Control: no-store`.
- Every inbound request receives a cryptographically random `tr_` trace ID in `X-Trace-ID`; error envelopes repeat the same ID.
- `/health/ready` returns `503 HEALTH_NOT_READY` with `Retry-After: 1` until migration, database write, and initial reconciliation readiness are wired in a later work package.
- `/version` reports build version, commit, build time, API version `v1`, and a sorted unique capability list. No later-phase capability is currently advertised.
- Unknown `/api/v1` resources return the registered JSON `RESOURCE_NOT_FOUND` error and never fall through to the SPA.
- `api/openapi.yaml` is the machine-readable API contract. Its `x-stackpilot-error-codes` extension is the error metadata source of truth; tests enforce alignment with the implementation registry.

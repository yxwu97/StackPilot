# P1B-01 Operation Foundation Evidence

- Operations and ordered structured steps persist in SQLite migration `000002_operations.sql`.
- A partial unique index enforces one `queued`, `running`, or `cancelling` Operation per workspace; terminal transitions release the database constraint.
- Idempotency is scoped by caller subject, route semantics, workspace, and key. Matching request digests replay the original Operation, mismatches return `IDEMPOTENCY_KEY_REUSED`, and keys expire after 24 hours without deleting Operation history.
- Operation and step state transitions are centralized. Cooperative cancellation immediately cancels queued work, moves running work to `cancelling`, and rejects cancellation of stop Operations.
- Step attempts increment only when entering `running`; retries clear prior error metadata and record the new attempt duration independently.
- Real SQLite tests cover creation, replay, key reuse, active-lock conflicts, terminal release, cancellation, illegal transitions, retries, simultaneous creators, version-one migration upgrades, and persistence across database reopen.
- Stable Operation errors are synchronized across the OpenAPI registry, API implementation registry, and human-readable error table.

Verified with `go test ./internal/domain ./internal/orchestrator ./internal/storage ./internal/api -count=1`.

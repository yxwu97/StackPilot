# P1B-09 Single-Service Use Case Evidence

- The application service creates persisted asynchronous start/stop Operations; HTTP returns `202` after queueing and never waits for Runner, process startup, readiness, or termination.
- Start uses the last valid immutable manifest snapshot, selects the single dependency-free Phase 1B root service, canonicalizes the working and instance paths, resolves the Runner, expands only approved templates, probes declared fixed ports, hashes the resolved specification, and runs Process Driver preflight before creating a business process.
- `system_instances` and `service_instances` now have a real SQLite repository. Service transitions are centralized, use optimistic `state_version`, and commit each state update with an Operation-scoped domain event in the same immediate transaction.
- Migration 6 persists each service's start-time graceful-stop timeout, so later stop/cancellation does not read a refreshed manifest or silently force the default policy.
- TCP and HTTP readiness verify the managed process identity before each network attempt, so an exited or replaced process fails immediately instead of waiting for the readiness timeout.
- The worker connects Runner resolution, Process Driver, Supervisor spool files, Log Manager capture, Health Engine readiness, aggregate state, Operation steps, and the persisted Event Broker notification path.
- Successful integration coverage exercises `queued -> running -> ready -> stopped` using real SQLite Operation, instance, health/event schema, and workspace snapshot repositories.
- Readiness failure retains the process identity, logs, failed service, and failed system by default. The stable readiness code is copied to the failed step and terminal Operation. `cleanupOnFailure=true` uses the bounded single-service cleanup path.
- Start cancellation is recorded durably before the worker context is cancelled. The test verifies process stop, capture close, service/system transition to stopped, and terminal `cancelled`; stop Operations are non-cancellable.
- Repeated stop with no active instance completes as an idempotent successful Operation with skipped stop/aggregate steps. Process identity paths and opaque platform tokens are not exposed by status or Operation DTOs.
- OpenAPI covers start, stop, status, Operation detail, and cancellation. Requests allow only workspace selection, declared port overrides, and failure policy overrides; they do not accept commands, arguments, working directories, or environment variables.

# P2B-01 Evidence - Compose manifest contract

Status date: 2026-08-18

P2B-01 is verified. The v1alpha1 Schema now defines a closed Compose driver branch without enabling incomplete container execution.

## Delivered behavior

- `driver: compose` requires `compose.file` and a nonempty, unique `compose.services` list.
- Compose service references use a bounded Compose-compatible name pattern and reject unknown fields.
- Compose is daemon-only, requires `readiness.type: compose`, and rejects process-only `runner`, `virtualEnvironment`, `workingDirectory`, and `arguments` fields.
- Process services continue to require their existing runner/working-directory/arguments contract and cannot select Compose readiness or carry a Compose definition.
- The Compose file must be a real regular file. Registration resolves its relative path through the existing handle-based Windows canonicalization and rejects missing files, symlink/junction escape, or paths outside the workspace.
- A structurally and semantically valid Compose manifest still returns `FEATURE_NOT_ENABLED` with feature `compose`; `/version` does not advertise `phase2.compose`.

## Verification

Schema tests cover valid Compose references, missing definitions, process/Compose field mixing, oneshot rejection, readiness mismatch, duplicate service references, and unknown fields. Manifest tests verify canonical file resolution, outside-workspace rejection, and the final capability gate. Existing Windows path tests continue to cover junction traversal through the same `ResolveWorkspaceFile` boundary.

No Docker command is executed by P2B-01. This is intentional: executable discovery, daemon access, and Compose config parsing belong to P2B-02, while registration remains disabled until the later runtime work packages close the half-implementation risk.
